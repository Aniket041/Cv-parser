# Local CV fine-tuning

Status: dataset preparation and a LoRA training entry point are implemented.
No trained adapter is bundled. Python rule changes and processing resumes do not
train model weights. The 2026-09-10 hardware check found an Intel i3-7100T,
about 16 GB RAM, Intel HD Graphics 630, and no CUDA GPU. The current machine
is suitable for preparing/reviewing labels, but not this GPU training workflow.

## Random batches of 100

From the project root, run:

```powershell
python -m training.dataset --count 100
```

Each run creates a new `data/training/batch_XXXX` directory. Sampling is seeded,
files are read locally, and previously selected file/text hashes are excluded.
Only likely text-readable CVs are selected; inspect `skipped.jsonl` for files
needing OCR or manual classification. This filtering is heuristic.

`examples.jsonl` contains original extracted text, source filenames, the reference
date, and draft answers. **Drafts are generated by the existing imperfect rules,
not supplied as correct answers by an expert or model.** They never train by
default. Review all nine fields against the CV, put corrected fields into
`answers`, set `reviewed_by` to the reviewer and `review_status` to `approved`.
Use `rejected` for non-CVs or unsuitable examples. The assistant can review these
files in subsequent sessions; do not bulk-approve drafts without inspection.

Corrections may alternatively be stored in `reviews.json` beside the JSONL,
keyed by example ID, with `answers`, `review_status`, `reviewed_by`, and
`review_notes`. The loader applies these without rewriting original source text
or drafts. Assistant review is identified explicitly and is not human certification.
`summary.json` describes preparation-time counts; use `reviewed_rows` or the
training loader to get current approval counts after correction sidecars.

Training and validation separation is fixed by candidate email where available,
otherwise normalized text. Different CV versions without a common email may
still overlap: review for identity leakage before evaluating. Exact duplicate
text is excluded. Use only authorized candidate data; text and contact fields
remain on disk in this ignored directory.

## Train on a GPU machine after review

1. Prepare a separate Python environment and install `training/requirements.txt`.
2. Download the Hugging Face **Qwen/Qwen2.5-3B-Instruct** model to a local folder
   during setup. The Ollama quantized download is not the training model folder.
3. With at least 20 approved training and 5 approved validation examples:

```powershell
python -m training.train_lora --base-model D:\models\Qwen2.5-3B-Instruct --output data\training_runs\run_001
```

The command requires CUDA and loads only local weights; no API key or uploads.
It trains q/v attention LoRA adapters, masks prompt tokens from the training loss,
and evaluates on held-out examples. Long CVs cause an explicit error instead of
silently truncating the source. More GPU memory is needed for larger contexts.
Rerun against all approved batches for each new training run to retain earlier
examples. The batch size of 100 is the review batch, not GPU minibatch size.

The generated adapter is not automatically installed in Ollama or connected to
the parser. Compare field-by-field accuracy against the base model first, then
integrate a validated adapter as a separate deployment step. Training loss alone
does not prove extraction accuracy. Training execution remains untested on this
machine because the training packages, HF weights and CUDA GPU are absent.

Implementation references: [PEFT LoRA](https://huggingface.co/docs/peft/package_reference/lora)
and [Transformers Trainer](https://huggingface.co/docs/transformers/main_classes/trainer).
